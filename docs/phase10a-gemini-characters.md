# Phase 10-A：Gemini 3.5による人物設定案

Gemini 3.5 Flash-Liteで正式脚本の人物設定案を作り、既存の確認・修正・部分採用・キャラクターバイブルへ接続します。無料モックが既定で、実送信には既存のテキストAPI設定と送信ごとの承認が必要です。接続実装済み・実通信未検証です。

## 実装前の棚卸しと再利用

|---|---|---|

## 生成から採用まで

1. **STEP 1：脚本を選ぶ** — 「キャラクター → AIキャラクター制作・一貫性管理」で最新の正式脚本を選びます。候補脚本・未確定・過去版から新規送信しません。
2. **STEP 2：抽出人物を確認** — 人物名、登場ページ・コマ、既存人物の照合候補を確認します。抽出自体は無料・オフラインです。描写だけの未登録人物は名前を追加指定できます。代名詞・不明話者は勝手に既存人物へ割り当てません。
3. **STEP 3：設定案を生成** — 「Gemini 3.5 Flash-Lite」と利用枠を選択し、送信内容・最大額・共通予算残額を確認します。承認チェック後に1回生成し、候補を保存します。同じ資料の保存済み依頼は再利用し、意図して再送する場合だけ既存の「同条件でも新しい人物提案を作る」と新しい承認を使います。
4. **STEP 4：修正・部分採用** — 既存人物は自動選択しません。新規か既存UUIDかを人間が選び、原文・区分・変更前後・同名/特徴の類似候補を確認します。「修正案だけを保存」は正式人物を変更しません。「この人物の選択項目だけを正式採用」は選択項目だけを反映し、未選択の設定・人物ID・基準画像を保持します。
5. **STEP 5：バイブルを保存** — 採用後のボタンから同じ人物の既存バイブル画面へ移動します。正式プロフィール・性格・人物関係、固定項目、別名、例外、参照状態、根拠を確認し、別の明示操作で新しい版として保存します。基準画像がなければ未登録のままで、画像の外見確認が完了したとは表示しません。

無料モック・既存手動JSONの取り込み・手動人物設定・旧内部ルート・6工程は残ります。長い生成画面、候補画面、共通予算画面の切替で旧ウィジェットが残らない固定領域を使用し、エラー後も最新の保存状態とボタンを表示します。入力の下書きは従来の仕組みで保持します。

## 人物JSONと根拠

既存の`characters`提案エンベロープを使います。依頼UUID・作品UUID・脚本版・候補IDを固定し、全候補を一度ずつ要求します。JSONの必須項目・型・余分なキー・重複・欠落・モデル・完了状態を受信後にも検証します。`existing_id`は必ずnullで、AIに既存人物の同定や採用はさせません。

生成する設定は、名前、役割、性格、年齢・性別、髪型・髪色、瞳、体格、服装、外見上の特徴、人物関係、作画時に維持する特徴です。登場ページ・コマはAIに捏造させず、抽出済みの脚本根拠を同じ提案に関連付けて表示します。

| 区分 | 扱い |
|---|---|
| ストーリー明記 | 対象人物の抽出原文と値を照合。複数人物の文から特徴を一人へ割り当てない。人物関係は原文全文を維持 |
| AI提案 | 脚本にない創作補助。人間の確認・修正前に正式設定とは扱わない |
| 未設定・要確認 | 空文字と要確認。画面では「未設定」と表示 |
| ユーザー編集 | 修正案の保存・部分採用で変更した内容。原案・編集履歴を保持 |

年齢・性別は特に保守的に、既存抽出器の設定ラベル（例：`年齢：17歳、性別：女性`）で一意な根拠がある値だけをAIが返せます。曖昧な文脈や推測だけなら空欄です。人間が値を確認して編集・採用することは可能です。モデルの解釈が引用の条件を満たさない場合、事実扱いへ自動修正しません。

「視覚的な差別化」(`visual_identity`)に作画時に維持すべき特徴を整理します。「他の登場人物との関係」(`relationships`)は既存人物設定の任意追加項目です。旧人物・旧提案・旧バイブルに存在しなくても読み込み可能で、自動移行しません。既存人物への部分採用でこの項目を選ばない場合、従来の項目欠如も保持します。旧形式の採用途中ジャーナルも再開できます。

## 接続・料金・送信範囲

- モデルは既存登録済みの`gemini-3.5-flash-lite`のみ。既存の2.5設定やOpenAI設定から自動切替しません。
- 「企画・脚本 → AI企画・ストーリー → 制作条件」の既存Gemini料金JSONを使います。人物用の料金設定や予算枠を別に作りません。
- 無料確認済みモードは`MANGA_ENABLE_TEXT_API=1`、有料モードは`MANGA_ENABLE_PAID_STORY=1`の既存フラグを使います。いずれも既定OFFで、キーは既存の`GEMINI_API_KEY`から取得します。
- 既存の提供状況・権限・規約・外部送信条件・料金根拠が未確認なら停止します。無料モードはアカウントの無料枠・残枠・データ条件の本人確認も必要です。
- 最大入力は既存モデルの全入力幅、出力は保存済み料金JSONの上限で見積もります。思考minimalも出力費用に含みます。モデル・単価・上限を今回変更しません。
- 外部へ送るものは正式脚本のテキスト、抽出候補と原文・登場コマ、保存済み人物の設定テキスト/ID、バイブルの設定・別名・固定項目・例外です。基準画像・コマ画像・音声・ファイルパスは送信しません。APIキーは認証ヘッダーだけで、本文・ログ・JSONへ保存しません。
- 共通の作品累計500円・全作品月間5,000円、正の最大予約、1承認につき1実行、請求不明時の全作品の停止を維持します。無料枠も有料相当額を予約する既存ルールです。これはGoogleの請求額や無料枠の保証ではありません。

料金例・無料枠の条件は[Phase 9-B3資料](phase9b3-gemini35.md)を参照してください。仮の為替150円/USD・税1.10・安全係数1.25、最大出力16,384なら、今回の最大予約例は73.328640円です。本人が保存した条件で計算し、固定金額を実行許可に使いません。

## 途中失敗・再起動

依頼状態は既存の`assistant.json`内の`character_ai`メタデータに追記します。候補も従来の`proposals`、原案も`original_payload`です。正式人物やバイブルの新しい正本は作りません。共通のAI生成ロックと台帳の実行権で競合を防ぎます。

API応答は、既存の`AIStoryStore.write/read`で`story_ai/character_responses/<request UUID>.json`へ上書きせず保存します。元の脚本/人物/バイブルの指紋、依頼ID、応答SHAを照合してから候補を公開します。生成中に元資料が変われば要再確認とし、古い候補を現在の人物へ反映しません。ハッシュは成果物/元資料の検証用で、APIキーのハッシュではありません。

| 状態 | 次の操作 |
|---|---|
| 処理中・中断 | 同じ依頼は再送しない。履歴のリクエストIDと共通台帳を照合 |
| 通信・請求確認待ち | 予約を保持。既存のAPI予算管理でGoogleの確定した請求を本人が照合 |
| 請求確定・候補保存前に失敗 | 「人物生成の保存を再開・請求を照合（再送なし）」から保存済み応答を再利用 |
| 応答が欠損 | 不明請求の間は停止。本人が請求を照合した後、候補なしの確認待ち記録を保持。必要なら新しい依頼を個別承認 |
| JSON不正・未完了 | 候補を自動採用せず履歴を保持。再生成は明示的な新規依頼と承認が必要 |
| 元資料変更 | 古い応答を履歴として保持し、最新の正式脚本・人物を確認。無断で新しい版に適用しない |
| 採用保存失敗 | 従来の採用ジャーナルから再開。他の編集があれば上書きしない |

API予算画面から人物画面への復帰ボタンを追加しました。過去の脚本版のAPI履歴も選べるので、脚本更新後の未確定請求を隠しません。元の共有台帳の保存先が異なる/欠損する場合、別の空台帳で送信せず停止します。アプリ終了直前に台帳の記録を残せなかった等、結果を証明できない状態は自動で未送信扱いにしません。

過去版の生成履歴から現在版の採用へは誘導しません。Gemini専用依頼に旧手動取り込み画面から別の応答を重ねて保存することも禁止します。従来の手動JSON依頼・無料モックは維持し、Gemini候補の項目修正は既存の人物確認画面で行います。

## Macでの確認

1. 作業ブランチへ切り替え、既存作品・共有台帳をバックアップします。`MANGA_DATA_DIR`と`MANGA_BUDGET_DB`を従来の永続保存先のままにします。台帳を削除・再作成しません。
2. 用意済みのPython 3.11または3.12の仮想環境で、必要に応じて`python -m pip install -r requirements-dev.txt`を実行します。通常起動は`python -m streamlit run app.py`です。
3. 最初は無料モックを選び、独立した架空の8ページ24コマ・2名の作品で、脚本登録 → 人間の最終確定 → 人物抽出 → 修正案保存 → 人物の同定・部分採用 → バイブル保存を確認します。基準画像がなくてもテキスト確認はできますが、画像は未完了のままです。
4. 通信なしで追加テストを実行する場合：

   ```bash
   python -m pytest -q tests/test_character_ai_gemini.py tests/test_character_ai_gemini_recovery.py tests/test_character_ai_gemini_compat.py tests/test_character_ai_gemini_app.py
   ```

   『桜色のタイムカプセル』相当の専用テスト作品・フェイク人物/画像・仮の料金条件・一時台帳を使います。既存データを使わず、ネットワークを拒否します。実際の人物一致や公開品質を保証するテストではありません。
5. **実通信を本人が行う場合だけ**、既存の接続設定・認証問題・請求未確定分を先に確認します。今回の開発でMacの実認証が直ったという意味ではありません。必要なら[認証調査資料](gemini-rest-auth-investigation.md)を使います。
6. 同じターミナルに安全に設定済みの`GEMINI_API_KEY`、既存の無料確認済みフラグ、証明書設定を使います。新しいキーの登録や有料モードの有効化は今回の必須条件ではありません。TLS検証を無効にしません。
7. 既存のGemini 3.5料金JSON・モデル権限・無料枠/データ条件を本人が確認・保存した後、人物画面でGeminiを選び、送信対象・最大額・共通残予算を確認します。個別承認して1回だけ生成します。エラー時は再送せず、履歴と台帳を確認します。
8. 候補を修正・部分採用し、旧人物UUID・基準画像・未選択項目が保持されることを確認します。バイブルは別操作で保存します。

Codexによる実API送信0回・無料枠消費0回・実費0円です。実機テストを実施したとは報告しません。
