# GitHub半自動連携の使い方

ChatGPT ⇄ GitHub ⇄ AI漫画スタジオの受け渡し機能です。OpenAI API・非公式API・ChatGPTの画面自動操作はありません。
ChatGPTを呼び出して処理を繰り返す仕組みではなく、GitHubにコミットされた新しい成果物を、利用者の操作で取得します。

## 最初の準備

- Python 3.11・Streamlit 1.40.2の既存環境を使います。実行パッケージの追加はありません。
- `git --version` が動くことを確認してください。MacでGitが未導入ならAppleのCommand Line Tools等で用意します。
- 非公開リポジトリの取得・作品ブランチへの保存には、そのリポジトリのContents読み書き権限が必要です。
- 認証情報は `GITHUB_TOKEN`（優先）、`GH_TOKEN` 環境変数、または `.streamlit/secrets.toml` の `GITHUB_TOKEN` で指定できます。指定がなければ既存のGit認証を使います。
- トークンを作品JSON・ソース・GitリモートURLに書かないでください。Secretsと `.env` は既存の `.gitignore` の対象です。画面に認証情報の入力欄はありません。
- 引き続き `MANGA_DATA_DIR` を外部フォルダに設定し、更新前にフォルダ全体をバックアップしてください。

6工程メニューは維持しています。入口は **完成・書き出し → GitHub作品同期** です。まだ作品を開いていない場合も、この画面から作品IDを指定できます。

## 取得 → 候補確認 → 明示採用

1. リポジトリ `shomasato-gitm/manga`、作品ID、取得ブランチ（初期値 `main`）を指定します。
2. 「GitHubから候補取得」で次の取得方法を選びます。
   - **作品スナップショット**：このアプリが保存した `works/<作品ID>/sync/latest.json` をたどります。
   - **既存worksファイル**：GitHubの一覧から、既存のストーリーJSON、任意の人物・作画指示JSON、画像とページ・コマの対応を選びます。
   - **AI提案・画像レビューの回答**：ローカルで作成した依頼に対応する回答JSONを選びます。
3. 取得ボタンを押します。固定コミットからファイルを読み、容量・ハッシュ・JSON・画像・ID・版を検証して **確認待ちの候補** に保存します。取得しただけでは正式作品は変更しません。
4. 「差分確認・明示採用」で候補を選び、ファイルの差分と、必要ならJSONの実際の変更値を確認します。
5. ストーリー、人物・作風・作画指示、画像候補、ページ編集から採用する範囲を選択します。初期値はすべて未選択です。
6. 画像は通常、候補に登録するだけです。同期元の画像選択も採用したい場合だけ専用チェックをオンにします。
7. 「差分と採用範囲を確認した」をオンにし、明示採用ボタンを押します。初めての作品なら作品情報もこの時点で登録します。

既存の `schema_version: 1` のストーリー形式は変更しません。新しい脚本は既存履歴を残して取り込みます。
同じ脚本や画像を再取得しても、取得日時や無関係なGitHubコミットだけを理由に版・画像候補を増やしません。生成元の脚本・人物・作画内容が変わった画像は別候補として保持します。
人物IDは一致するIDで照合し、名前から勝手に付け替えません。同名・別ID、同じ画像IDで異なるハッシュ、固定した基準画像IDの変更は停止します。
基準画像の追加時も既存参照と過去候補を維持します。削除済み人物の復活・リモートからの削除伝播・過去版への自動巻き戻しは行いません。
作画・画像・ページ編集の採用には対応する脚本版が必要です。古い画像・編集は既存の品質チェックで再確認できます。

### 今回の作品を初めて取り込む例

作品ID：`2d83c11f-04ee-4134-a66d-dace81c6f698`（『君が忘れた、最後の約束』）

「既存worksファイル」で次を選びます。

- 脚本：`story_test_revision_2026-10-17.json`
- 人物・作画指示：`artwork_directions_test_2026-10-17.json`
- 参考資料：必要なら `editorial_test_review_2026-10-17.json` と `page_01_composition_manifest_2026-10-17.json`
- 画像：`夕暮れの教室、交差する青春.png` → 1ページ1コマ
- 画像：`夕暮れの教室、二人の視線.png` → 1ページ2コマ
- 画像：`夕暮れの教室、涙色のまなざし.png` → 1ページ3コマ

画像の選択順にかかわらず対応するコマ番号を確認してください。ファイル名にUnicodeの結合文字がある画像も、そのまま扱います。
この旧作画提案形式は既存の人物・作画バリデータで確認できる候補へ変換します。元の提案は候補内の参考資料として保持します。
任意のJSONを推測で別形式へ変換する機能ではありません。未知の形式や不足した必須項目はエラーにします。
元資料でも人物の正式な基準画像は未照合です。3枚のコマ画像を人物基準画像として勝手に扱いません。

## JSONの手動コピーを減らす制作運用

- ChatGPTへの依頼・画像添付・送信は引き続き手動です。GitHubの読み書き可否は、ChatGPT／Codex側で実際に使える連携機能と権限に従います。
- 対応する書き込み機能がないChatGPT画面から、アプリが代理でGitHubに保存することはありません。その場合はGitHubのUpload filesやGitを使ってファイルをコミットします。
- 新しい脚本は `works/<作品ID>/drafts/<一意の名前>.json` 等に保存し、アプリからそのファイルを選べます。元の正式ファイルを上書きする必要はありません。
- キャラクター・作画指示等のAI一括提案では、まず既存アプリで依頼を作成します。依頼と脚本・人物設定を作品スナップショットに含めてGitHubへ保存すれば、ChatGPT側で依頼IDや設定を参照できます。
- 回答は `works/<作品ID>/responses/<一意の名前>.json` 等にコミットし、「AI提案・画像レビューの回答」で取得します。
- `request_id`、作品ID、脚本版、人物ID、対象コマを既存の検証処理で照合します。画像レビューの回答は画像や編集設定が変わると取り込めません。最新の依頼を作り直してください。
- 候補画面から回答を登録しても、既存の制作アシスタントでは「確認待ち」、画像レビューでは「未確認の提案」のままです。正式採用・タスク化は既存画面で別途行います。

これにより返答JSONの貼り付け・ローカルダウンロード・再アップロードをGitHub取得へ置き換えられます。既存のファイル取り込み・貼り付けも残しています。

## 完成PNG・PDFと採用済みデータを保存する

1. 既存の「PNG・PDF書き出し」でファイルを生成します。
2. **この完成ファイルをGitHub同期用にローカル保存**を押します。これはまだGitHubへの送信ではありません。
3. 同期画面の「GitHubへ保存」を開き、保存先の作品ブランチを指定します。初期値は `studio-sync/<作品ID>` です。
4. 必要な保存済み完成PNG・PDFを選び、「送信対象と容量を確認する計画を作成」を押します。
5. **この作品1件**のJSON、人物参照、画像候補と採用対応、指定した完成ファイルの一覧・容量を確認します。
6. 公開範囲を確認してチェックを入れ、GitHubへ保存します。公開リポジトリのファイルは閲覧可能になります。

`data/projects/` 全体の自動アップロードはありません。GitHubへ書くのは `works/<作品ID>/sync/<スナップショットID>/` と、その作品の `sync/latest.json` だけです。
PNG・PDFはbase64テキストファイルにせずバイナリとして保存します。以前のスナップショットを削除・書き換えず、ポインターだけを新しい版に更新します。
`main`／`master` へのアプリからの保存は拒否し、マージもしません。必要ならGitHub上で内容をレビューして作品ブランチのPRを作成してください。

完成ファイルの生成後に脚本・画像・配置が変わった場合は、古い成果物の送信を止め、作り直しを案内します。
GitHubから得た完成ファイルは候補の詳細欄からダウンロードでき、既存の完成ファイルを自動置換しません。

## 品質確認とPDCA

「品質・PDCA・履歴」で次を記録します。

- 改善回数上限：初期値3回（1〜100回）
- 参考評価点の品質基準：初期値80／100点
- 未確認を含む今回の点数・対象候補・脚本版・同期元コミット
- 利用者の確認、次のGitHub成果物待ち、上限到達、停止理由
- 基準変更・取得・採用・公開の履歴

次の作業は既存の「品質チェック・修正管理」で自動検査・ページ目視・修正タスク・再確認を行います。
全ページの最終確認、未解決タスク、未確認AIレビュー、評価対象の脚本版を既存機能から照合します。点数が基準以上でも未確認なら品質達成にはしません。
上限に達した後に勝手に続ける処理はなく、利用者の停止理由も記録できます。点数は主観的な参考値であり作品品質の保証ではありません。
他端末の `review.json` や編集評価の履歴は検証した候補資料として保持しますが、その目視合格を現在のローカル作品へ自動移植しません。ローカルの既存レビューとタスク履歴は維持します。
旧資料の独自評価軸を既存評価の点数に推測変換しません。正式な評価形式とは別の参考資料として保管します。

## 競合・失敗時の動作

- 同期履歴の版、候補取得時のローカルの内容ハッシュ、GitHubコミットを比較します。
- 前回の同期後に両側の同じJSONが変わった場合、同期を停止しファイル・JSON差分を表示します。自動マージ・リモート優先上書きはありません。
- 候補取得後にローカル／GitHubが変わった場合も採用を止めます。最新の内容を確認して再取得してください。
- 保存計画後にローカルやGitHubが変わった場合、pushを止めます。競合を力ずくで上書きする操作はありません。
- ローカル採用は既存機能と同順のファイルロックで保護し、変更前後のファイルを保存してから原子的なJSON置換を行います。
- 複数ファイルの採用途中に失敗した場合は、同期画面の「同期の採用保存を再開」を使います。途中で別の編集があれば復旧も停止します。先にフォルダ全体をバックアップし、エラーに示された差分を確認してください。
- 採用途中は他の制作画面で編集しないでください。既存ストアへロック機構以外の大幅な変更は加えておらず、各画面の単独保存を一括トランザクションに置き換えてはいません。
- GitHubの保存だけ成功してローカルの送信記録が失敗した場合は、同じスナップショットの全内容を照合して記録を復旧できます。二重pushは行いません。
- 通信失敗時に認証ヘルパーの出力やトークンを画面・同期履歴へ保存しません。

## 容量と既知の制約

- 同期対象：1ファイル10MiB、1回合計100MiB、300ファイルまで。JSONは1件8MiBまでです。manifest・ポインターにも容量検証を適用します。
- 完成PNG・PDFのローカル保存：1作品合計100MiBまで。上限到達時も自動削除しません。
- Git LFS・大容量ファイルの分割転送・SNS ZIPのGitHub保存・リモート削除・背景の自動同期は未対応です。
- 通信は通常のHTTPS Gitです。初回は浅い履歴を取得してキャッシュするため、対象作品以外の同一コミットのGitオブジェクトもキャッシュされることがあります。公開するファイルは選択した作品に限定します。
- 旧作画提案アダプターは、今回の `characters`／`panels`／`source_description` 形式と既存の標準ストア形式に対応します。他の独自形式は既存形式へ整えてください。
- 人物の顔の一致や、画像に描かれた文字の画像認識はしません。
- スナップショット内のフォントパスは端末ごとに異なる場合があります。読み戻した端末で既存の出力設定を確認してください。
- Intel Mac・Python 3.11で使える標準ライブラリと既存依存のみを使用しています。Mac実機の認証・キーチェーン動作は別途確認が必要です。画像の採用確定には同一フォルダ内のハードリンクを使用するため、APFS／HFS+等の対応するローカル保存先を使ってください。

## 保存場所とコードの分担

`<MANGA_DATA_DIR>/<作品ID>/` の下に、次を追加します。既存のJSON形式は変えません。

- `github_sync.json`：候補、送信計画、取得元、版、採用範囲、PDCA、履歴
- `github_sync_pending.json`：採用途中の再開記録
- `github_sync/candidates/`：候補本体・manifest・採用時比較の基準
- `github_sync/exports/`：利用者が確認する送信計画のファイル
- `github_sync/transactions/`：ローカル変更前後の保全
- `github_sync/git/`：Gitキャッシュ
- `sync_outputs.json` と `sync_outputs/`：利用者が保存した完成PNG・PDF

`manga/github_sync.py` が取得・差分・明示採用・公開を調整し、`sync_manifest.py` が契約・容量・ハッシュ・実差分、`git_transport.py` が通信を担当します。
ローカル保存、既存バリデータへの接続、旧資料変換、採用、AI返答、PDCA、完成ファイル、UIは `sync_*.py` に分割しています。

## 検証の再現

ネットワークなしの既定の検証：

```bash
python -m pytest -q
python scripts/verify_github_sync.py --output /tmp/manga-sync-verification
```

空の専用フォルダに、指定作品の読み取り専用コピーから8ページ・24コマ・カラー画像3枚を作成し、一時bare Gitで往復します。既存作品ファイルへ書き込みません。
実GitHubでの検証は明示オプションのみで、専用 `studio-sync-test/` ブランチに限定します。

```bash
python scripts/verify_github_sync.py --github --output /tmp/manga-sync-github-verification
```

このコマンドは対象リポジトリに新しい検証ブランチ・スナップショットを保存します。`main`への書き込み・マージ・既存画像の削除は行いません。
検証記録には対象コミット、人物ID、画像SHA-256、往復結果、元資料の保持を記録します。
提供画像は1ページの3枚だけなので、検証PDFの他ページはプレースホルダーです。8ページの漫画の品質確認が終わったとは判定しません。
