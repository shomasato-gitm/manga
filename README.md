# AI漫画スタジオ（品質チェック・GitHub半自動連携対応）

漫画の企画を保存し、**ユーザーがChatGPTと手動で受け渡しして**ストーリーを制作するStreamlitアプリです。
プロジェクト作成に加え、プロンプト生成、ストーリーJSONの取り込み、ページ単位の編集、履歴の保存・復元ができます。
第3段階ではキャラクター設定・参照画像、コマ別の作画指示、画像生成用プロンプト、候補画像の登録・採用を管理します。
さらに、参考作品の分析、版に紐づくAI評価、選択した範囲の改善、実際のJSON差分比較、脚本の採用・確定に対応しています。
第4段階のページ合成・出力を、第8段階でトリミング、話者別分割、文字量に合わせたサイズ調整、ドラッグ編集へ拡張しました。
第5段階では、キャラクター・参考作品・全コマの作画指示をAIへまとめて提案させ、JSONを確認・編集・選択採用できます。作画の評価・改善、画像プロンプトの一括出力にも対応します。
第9段階では、保存済み漫画の自動検査、ページ単位の目視確認、修正タスク、任意のChatGPT画像レビュー、最終確認を追加しました。

**従来の手動漫画制作・既定モックはAPIキー不要です。非公式API・ChatGPTのWeb画面の自動操作は使用しません。**
手動連携・モック・ローカル動画生成では、AIサービスへの送信・API追加課金はありません。
任意のAI企画・脚本制作はOpenAI Responses、任意の音声制作はAmazon Pollyへ、別途の明示承認・認証・共通予算確認後に接続できる構成です。初期状態では両方の有料機能を無効にしています。
ChatGPTへの貼り付けと返答のコピーはユーザーがご自身のWeb画面で行います。ChatGPT側の利用制限は契約プランに従います。
画像生成はユーザーがChatGPTで行います。アプリは生成された画像をローカル保存し、採用画像から漫画ページを合成します。

**企画・ストーリー → AI企画・ストーリー**から、ジャンル・テーマ・ページ数・雰囲気を入力します。
企画3〜5案を比較・選択し、コマ単位の脚本生成→8項目評価→改善→再評価を最大5回まで実行できます。
目標点・回数上限・品質低下・予算不足等で停止し、実際のJSON差分と評価を比較して任意の候補を明示採用します。
既定は無料モック。有料APIはモデル・料金の公式確認と別途承認が必要で、必ず共通BudgetedExecutorを通します。

候補はstory_ai.jsonへ分離し、正式採用時だけ旧形式の脚本・対応する評価を新しい履歴として追記します。既存の人物・画像・音声・動画は変更しません。

## AIキャラクター制作・一貫性管理（Phase 2-C、無料モック）

**キャラクター・作風 → AIキャラクター制作・一貫性管理**で、最新の正式・確定脚本から人物候補を抽出します。
原文の根拠と既存人物の照合候補を確認し、人物UUIDの反映先と採用するフィールドを自分で選びます。未採用案では正式人物を変更しません。

## モーションコミックの3形式MP4出力（Phase 4、任意）

**完成・書き出し → 動画制作・MP4出力**で、採用PNG・保存済みWAV・字幕タイムラインを使います。
YouTube本編1920×1080、TikTok／Shorts各1080×1920をH.264/AACで生成します。
縦型2種類は独立したコマ・発話選択、順序、注目領域、字幕・フック文を編集できます。
緩いズーム・パン、カット／フェード、日本語字幕、任意の利用権確認済みBGM/SFX、静止画プレビュー、MP4再生・ダウンロード・再出力に対応します。

FFmpegのみのローカル処理で、**動画工程から有料AI APIは一切呼び出しません**。ffmpeg／ffprobeがない場合は動画機能だけを停止します。
元の画像・音声・ストーリーを変更せず、`video.json` と `video/` に独立保存します。生成済み・確認用トーン・目標尺未達・未確認素材を区別し、公開前の人間の確認を必要とします。
目標3〜5分／45〜75秒に満たない素材を水増しせず、実尺を表示します。

操作、FFmpeg導入、Macでの確認、保存・中断復旧は **[動画制作ガイド](docs/VIDEO_RENDERING.md)** を参照してください。

### コマ制作ワークスペースの使い方

1. プロジェクトを開き、ストーリーJSONを登録します。「キャラクター・作風」で人物・作風・基準画像を用意します。
2. 「絵コンテ・作画指示 → AI一括生成・採用」で指示を採用したら、**「採用したコマのイラスト制作へ」**を押します。手動で進める場合は「イラスト制作 → コマ制作ワークスペース」を開きます。AI評価・改善は任意です。
3. 対象ページとコマを選び、描写・作風・登場人物・現在の制作状態を確認します。「作画指示を編集」をオンにすると、このコマだけ調整できます。未設定・要確認の指示は初期状態から編集できます。
4. **「このコマの作画指示を保存」**で確定します。未保存の変更がある間は画像登録・採用を止めます。空欄の任意項目を推測で埋めません。
5. 同じ画面の「依頼プロンプトをダウンロード」またはコピーを使います。全文は初期状態で折りたたみます。「登場人物の設定・基準画像」では登録済み参照画像を確認し、「○○の元画像を取得」をオンにして原寸PNGをダウンロードできます。
6. **ユーザーがChatGPTへプロンプトと参照画像を手動で渡し、画像を生成・ダウンロード**します。アプリに戻り「このコマの候補画像」→**「候補画像を保存」**を押します。
7. 候補を見比べます。必要なら「2候補を並べて比較」をオンにします。「採用候補を選ぶ」→**「選んだ候補を採用」**で確定します。登録だけでは採用されません。
8. 上部の**「次の未完成コマへ」**で続けます。「前のコマ」「次のコマ」はページをまたいで移動します。例えば1ページ3コマ目の次は2ページ1コマ目です。必要な指示・採用画像が全部そろうと**「漫画ページ編集へ進む」**を表示します。

「全ページ・全コマの進捗と移動」を開くと、24コマを含む現在のストーリー全体を一覧表示します。
作画指示の有無と、画像の未登録・候補あり・採用済みを別々の列で表示し、ストーリー変更・設定変更・画像の欠損があれば「要確認」にします。
「未完了コマへ移動」→「このコマの画像管理を開く」で直接移動できます。「絵コンテ・作画指示 → コマ一覧・制作へ」でも同じ進捗を確認できます。
現在のコマの候補のみを最大6枚ずつ縮小表示し、全ページの画像を一度に読みません。
「イラスト制作 → 画像履歴」はページ別の採用画像と、現在のストーリーから外れたコマの過去候補を閲覧する画面です。

コマの切り替えでは自動保存しません。欄外クリックなどでアプリが受信した下書きは、ストーリー版・ページ・コマ・確定指示ごとにセッション内で保持します。
別コマの画像登録・採用をしても、元のコマの未保存入力を保持します。ストーリー版や対象コマの確定指示が変わった場合は、古い下書きを自動適用せず、警告と「以前の未保存入力をJSONで取得」を表示します。
保存済みの指示を更新できた場合は、その下書きだけを終了します。競合・保存失敗時はエラーを表示し、再試行できるよう入力を保持します。
ブラウザ再読み込み・セッション終了で未保存の入力は失われます。画像ファイル選択も、移動後は再選択が必要な場合があります。

ストーリー変更で古くなった指示は確認して保存し直してから画像を登録します。採用画像のある指示を変更すると、画像と合わなくなる可能性を通知します。
既存の人物ID、参照画像、画像候補、採用履歴、評価・改善履歴は維持し、勝手に再生成・削除しません。
第8段階では「漫画ページ編集」に画像トリミングと吹き出しのドラッグ編集を追加しました。コマ制作画面には、保存済みコマ割りの想定アスペクト比を表示し、画像生成プロンプトにも人物配置・吹き出し用の余地・重要な対象を切らない指示を含めます。未保存ページは標準レイアウトの想定と明記します。

### 次の操作と進行状況

「企画・ストーリー → ホーム・進行状況」上部の「次にやること」から、未完了の必須工程へ直接移動できます。
ホームでは6工程に集約し、「工程内の詳しい進行状況」で企画・ストーリー・人物・作風／基準画像・指示・任意の評価・コマ画像・合成・出力を確認できます。任意の評価は必須工程の完了判定を妨げません。
「未着手・進行中・完了・要確認」は保存済みデータから判定します。依頼を作っただけでは、人物登録・指示採用・出力を完了にしません。
参考作品と作画評価は任意で、実施しなくても次へ進めます。

人物は登録人数、基準画像は登録状況、作画指示と画像は全コマの保存・採用状況を確認します。
脚本変更後の指示、設定変更後の画像、欠けた画像ファイルなどは要確認になります。
ページ合成と出力は、現在のストーリー版・作画設定・ページ設定・画像ファイルの条件で実際に成功した記録を使います。
単にレイアウトを保存しただけでは全ページ合成完了にはしません。
出力完了は**ファイル生成の記録**であり、利用者のダウンロードフォルダへの保存完了を保証しません。取得したファイルも確認してください。

「イラスト制作 → コマ制作ワークスペース」では、全ページ・全コマの
「作画指示未設定／画像未登録／候補あり／採用済み」と要確認を一覧表示します。
「未完了コマへ移動」で選び、「このコマの画像管理を開く」で該当箇所へ移動できます。

### JSON取り込みとプロンプト取得

すべてのJSON入力は、初期値が **JSONファイル** です。「貼り付け」へ切り替えることもできます。
依頼作成後は、依頼ID・ストーリー版・対象コマと「依頼プロンプトをダウンロード」が長文の前に表示されます。
コピー機能を利用できるブラウザでは「プロンプトをコピー」も使えます。制限されている場合はダウンロードしてください。
全文は「詳細を表示（プロンプト全文）」をオンにした場合だけ表示します。
取得→ChatGPTへ手動送信→JSONファイルを戻す→検証→差分確認→明示的な採用の順で進めます。
依頼作成・検証・画像保存・採用・プレビュー・出力には処理中／完了／エラーを表示します。
全ページ出力・縦読み出力は、実際に描画したページ・コマの件数を表示します。取得できない処理時間から進捗率を推測しません。
失敗時はエラーの理由を確認し、入力・権限・空き容量・最新の版を見直して再試行してください。

### 入力の下書きと表示量

入力後は欄外をクリックするなどして入力を確定してからメニューを切り替えてください。

「完成・書き出し → 保存先・容量・診断」で保持用の下書きを破棄できます。保存済みデータは削除しません。

提案一覧は12件、参照画像・候補ギャラリーは6件ずつ切り替えます。

## Intel Macでの準備

推奨環境は **Intel Mac・macOS 10.15〜12・Python 3.11** です。
主要な依存パッケージを、古いIntel Mac向けのバイナリ配布があるバージョンに固定しています。
Python 3.9〜3.12に対応する構成ですが、まずは3.11を利用してください。
macOS 10.14以前はPyArrowの配布対象外のため、この構成では対応しません。
Mac実機での動作確認は未実施です。

1. Pythonがなければ [Python公式のmacOSダウンロード](https://www.python.org/downloads/macos/) から、macOSの対応条件を確認してPython 3.11をインストールします。OS付属のPythonは変更しません。
2. ターミナルを開き、ダウンロードまたはcloneした `manga` フォルダに移動します。
3. 以下を1行ずつ実行します。`.venv` は、このアプリ専用のPython環境です。

```bash
cd /path/to/manga
python3.11 --version
python3.11 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m streamlit run app.py --server.address 127.0.0.1
```

`/path/to/manga` は実際のフォルダのパスに置き換えてください。
ブラウザが自動で開かなければ、ターミナルに表示されるLocal URLをブラウザで開きます。
終了するにはターミナルで `Control + C` を押します。
次回からはフォルダに移動し、`source .venv/bin/activate` と起動コマンドだけで起動できます。

すでに利用している場合は、アプリを終了してデータフォルダをバックアップした後、
次の手順でコードを更新して再起動してください。依存パッケージも同期します。第9段階も実行用パッケージの追加はなく、既存JSONの移行操作も不要です。

`git pull --ff-only` がローカルの変更などで失敗した場合、強制リセットをせず、変更を保存してから対応してください。

3. 左側の一覧から選び、「選択したプロジェクトを開く」で再読み込みします。
4. 読み込んだ内容を変更して保存すると、同じプロジェクトを更新します。
5. 「新規プロジェクト」でフォームを空にすると、別のプロジェクトを作成できます。同じタイトルでも別々のIDで管理します。

## ChatGPTとストーリーを作る手順

1. プロジェクトを作成・保存するか、一覧から開きます。通常は8ページにします。
2. 「企画・ストーリー → 生成・取り込み」を開きます。保存済みの設定から、全ページ・各ページ3コマを想定したプロンプトが自動で作られます。
3. 上部の「プロンプトをコピー」または「依頼プロンプトをダウンロード」を使います。全文を読みたい場合は「詳細を表示（プロンプト全文）」をオンにします。
4. ご自身でChatGPTを開き、新しい会話に貼り付けて送信します。
5. 返されたJSONをコピーし、アプリの「生成・取り込み」→「取り込み方法」→「貼り付け」に貼り付けます。またはUTF-8の `.json` ファイルに保存し、初期選択の「JSONファイル」から選びます。
6. 「検証してストーリーを保存」を押します。形式やページ数が不正なら、問題の場所を表示し、既存ストーリーは変更しません。成功すると新しいバージョンとして保存します。
7. 「企画・ストーリー → ページ編集」でページを選び、概要、各コマの描写・セリフ・ナレーションを編集します。「このページを保存」で、他のページを保ったままストーリー全体を履歴保存します。タイトルと全体のあらすじも編集できます。
8. 評価・改善したい場合は「企画・ストーリー → ストーリー評価・改善」で対象版を選び、評価JSONを取り込みます。その評価から改善用プロンプトを作成し、改善版JSONを新しい履歴として保存します。詳しくは次の節を参照してください。
9. 元に戻す場合は「企画・ストーリー → ストーリー履歴」で過去版を選び、内容を確認して「このバージョンを復元」を押します。復元も新しい版として保存するため、それまでの履歴は消えません。

プロンプト・JSONのダウンロードは**最後に保存した内容**が対象です。
ページやプロジェクトの切り替え、新しい取り込み、履歴の復元の前に、編集中の内容を保存してください。
受信済みの未保存入力は同じ版・同じブラウザセッション内で保持します。新しい取り込み・復元で版が変わる前には保存してください。
企画のページ数を変更しても既存ストーリーは自動で増減しません。画面に差異を表示し、次の取り込みでは新しい設定ページ数を検証します。

### ChatGPTなしで取り込みを試す

8ページのプロジェクトを保存して、[examples/story_8pages.json](examples/story_8pages.json) を取り込むと、24コマのサンプルを編集できます。
自分でJSONを作る場合は、画面の「JSONひな形をダウンロード」も利用できます。ひな形の記入用の文は実際の内容に置き換えてください。

### 受け渡すストーリーJSON

| 項目 | 形式・内容 |
| --- | --- |
| `schema_version` | 1。省略時も1として扱う |
| `title` | タイトル（100文字以内）。省略時はプロジェクトのタイトル |
| `summary` | 全体のあらすじ（4000文字以内）。省略可 |
| `pages` | 設定したページ数の配列。通常8ページ、1から順に並べる |
| `pages[].page` | 1からのページ番号 |
| `pages[].summary` | ページ概要（2000文字以内）。省略可 |
| `pages[].panels` | コマの配列。目安3コマ、1〜6コマを許可。3以外は警告を表示 |
| `panels[].panel` | 各ページ内で1からのコマ番号 |
| `panels[].description` | 必須の描写（4000文字以内） |
| `panels[].dialogue` | 話者を含むセリフの文字列（4000文字以内）。省略可 |
| `panels[].narration` | ナレーション（2000文字以内）。省略可 |

多少の出力の揺れは、取り込み時に次のように正規化します。

- JSONの前にUTF-8 BOMがあっても読み込みます。説明文の中に1つだけある ` ```json ` コードブロックも読み込めます。
- `{"story": {...}}` や `{"ストーリー": {...}}` の外側のオブジェクトを許可します。
- `タイトル`、`あらすじ`、`ページ`、`ページ番号`、`概要`、`コマ`、`コマ番号`、`描写`、`セリフ`、`ナレーション` などの日本語キーを許可します。
- `page_number` / `panel_number`、描写の `scene`、セリフの `dialogues` にも対応します。
- ページ・コマ番号が省略されていれば配列順から補います。`"1"` などの数字文字列も整数に変換します。
- セリフは文字列の配列、または `{"speaker": "話者", "text": "セリフ"}` の配列でも取り込めます。話者の `character` / `話者`、本文の `セリフ` も使えます。改行区切りの文字列として保存します。
- 任意の本文項目の省略・`null` は空文字列にします。未知の項目は保存せず、項目名を警告します。必要な情報なら対応項目に移してください。

番号の重複・欠番、ページ数の不一致、空の描写、同じ意味の項目の矛盾、未対応のバージョンはエラーです。
複数のコードブロックは1つに絞ってください。JSONは1MB以下・UTF-8形式とし、全角引用符、コメント、末尾の余分なカンマは修正してください。

## 参考作品の分析・評価・ブラッシュアップ

制作状況を「参考作品登録 → 参考作品分析 → ストーリー作成 → AI評価 → AI改善 → 再評価 → 脚本確定」の順に表示します。
状態は保存済みの記録から計算し、未実施のAI処理を完了と表示しません。参考作品の登録・分析は任意です。

### 1. 参考作品を管理する

「参考作品管理」で作品名、媒体（漫画・小説・映画・アニメなど）、ジャンル、参考にしたい理由、
好きなシーン・演出の概要、参考にしたい技法、参考にしたくない要素、出典URL、メモを登録します。
作品名と媒体は必須です。各項目は2000文字以内とし、著作物の本文や固有のセリフの大量コピーではなく、ご自身の短い要約・観察を記入してください。

一覧から選んで編集できます。削除時は確認チェックを入れます。削除は一覧から外す方式で、分析履歴は保持します。
URLは出典のメモとして保存するだけで、外部サイトの閲覧・取得・スクレイピングは行いません。

### 2. 分析プロンプトと分析JSON

1. 「参考作品分析」で対象作品を選び、プロンプト枠の右上からコピーしてChatGPTへ渡します。
2. 導入、主人公の目的・欲求、キャラクターの魅力、感情、伏線と回収、意外性、セリフ・沈黙・視覚的演出、クライマックス、結末の余韻の9項目を分析します。
3. ChatGPTの分析JSONを貼り付けるかUTF-8ファイルで取り込み、「分析JSONを検証して保存」を押します。
4. 「分析メモの履歴」で過去の結果も確認できます。

登録情報は確認済みの作品本文とはみなさず、情報不足や未確認の場面は「不明」とするプロンプトです。
分析には根拠と確認状態を記録します。アプリは作品内容を検証していないため、ユーザーも結果を確認してください。
登録内容を編集すると版番号が変わります。編集前の分析を新しい内容の結果として取り込もうとした場合はエラーになります。

分析JSONはプロンプトに含まれるひな形を使います。

| 項目 | 内容 |
| --- | --- |
| `schema_version` | 1 |
| `reference_id`, `reference_version` | プロンプトに記載された作品ID・登録内容の版番号。そのまま返す |
| `aspects` | `opening`, `goal`, `characters`, `emotion`, `foreshadowing`, `surprise`, `expression`, `climax`, `ending` の9項目 |
| 各項目の `analysis` | 分析文。不足情報は不明と明記 |
| `abstract_technique` | 他作品の固有の表現を再現しない、抽象的な技法 |
| `basis`, `status` | 根拠と「ユーザー要約に基づく」「未確認」「不明」のいずれか |
| `unknowns` | 不明点・追加で必要な情報 |

### 3. 技法を参考にオリジナル脚本を作る

「ChatGPT用プロンプト」で参考作品を0〜3作品選べます。参考なしでも従来どおり生成できます。
登録した抽象的な技法と、現在の登録内容に対応する分析のうち「ユーザー要約に基づく」技法を組み合わせます。
古い版の分析や、シーン概要そのものはストーリー生成プロンプトへ渡しません。

プロンプトはオリジナルの人物・世界観・設定を使い、既存作品の固有の展開・場面・セリフを再現しないよう指示します。
登録済みのキャラクター設定も含めます。標準は8ページ・各ページ約3コマで、ページ数は企画の設定を使います。
生成結果は既存のストーリーJSONとして「JSON取り込み」から保存します。

### 4. ストーリーを評価する

1. 「企画・ストーリー → ストーリー評価・改善」で評価対象の版を選びます。初稿や過去版も評価できます。
2. 評価プロンプトをChatGPTへ手動で渡し、**評価用JSON**を受け取ります。
3. 「評価JSONを検証して保存」を押します。評価は選んだ版に紐づき、ストーリー自体は変更しません。
4. 同じ版を何度も評価できます。「使用する評価履歴」で過去の評価も確認できます。

評価項目は、導入の魅力、キャラクターの魅力、ストーリー構成、感情の盛り上がり、セリフの自然さ、伏線・回収、結末の余韻、オリジナリティの8項目です。
各0〜10点で、総合点は **8項目の合計 ÷ 80 × 100** を小数第2位までアプリが計算します。AIが別の総合点を返しても採用しません。
採点はAIの主観であり、客観的な品質や改善効果を保証しません。この注意を画面にも表示します。

| 評価JSONの項目 | 内容 |
| --- | --- |
| `schema_version` | 1 |
| `story_version_id` | プロンプトに記載されたストーリー版ID。そのまま返す |
| `criteria` | `opening`, `characters`, `structure`, `emotion`, `dialogue`, `foreshadowing`, `ending`, `originality` の8項目 |
| 各項目の `score` | 0〜10の数値。数値文字列も許可。NaN・無限大・範囲外は不可 |
| `good_points`, `problems`, `reason`, `suggestion` | 良い点、問題点、改善理由、具体的な改善案。不要な場合も「なし」等を記入 |
| `targets` | `[{"page": 1, "panel": 2}]` のような実在する対象。ページ全体は `panel:null`、全体の指摘は `[]` |
| `summary` | 総評 |

評価・分析JSONも1MB以下・UTF-8で、BOM、1つのJSONコードブロック、日本語キーに対応します。
不正な形式、対象版IDの不一致、存在しないページ・コマ、点数の不足・不正はエラーになり、既存データを変更しません。
ストーリーJSONは従来の取り込みへ、評価JSONは評価の取り込みへ戻してください。

### 5. 改善して、もう一度評価する

評価履歴を選び、改善したい項目と以下の方式を選択します。

- **全体を改善する**：選んだ項目の指摘を踏まえ、脚本全体を改善する。
- **特定のページ・コマだけを改善する**：対象を1件以上選び、その範囲だけを変更する。
- **特定の評価項目だけを重点的に改善する**：選んだ評価項目に集中し、無関係な改変を避ける。

追加の改善希望と「今回の改善理由・メモ」を確認し、改善プロンプトをコピーしてChatGPTへ渡します。
元のテーマ・世界観・人物設定・外見を維持する指示を含めますが、意味や表現の適切さはユーザーが結果を確認してください。

改善結果も**全ページを含む従来のストーリーJSON**です。「改善版を検証して新しい版に保存」から取り込むと、
改善元の版、使用した評価、方式、対象、理由を新しい履歴に記録します。元の版や評価は削除しません。
改善版のページ数は改善元に合わせます。企画側のページ数を変更している場合も、改善対象の版のページ数を維持します。
部分改善では、指定外のページ・コマ、タイトル、全体のあらすじが変わっていたら、実際のJSON差分で検出して保存を拒否します。
ページだけを指定するとそのページ内を変更できます。コマだけを指定した場合、ページ概要なども変更できません。

改善後は自動で新しい版が評価対象になります。新しい評価プロンプトをChatGPTへ渡し、返答の評価JSONを保存してください。
何度でも手動で改善・再評価を繰り返せます。通常の「JSON取り込み」でも改善版は保存できますが、改善元・理由との対応は自動では記録されません。

### 6. 比較・採用・脚本確定

「比較・脚本確定」で初稿・修正版・再修正版の点数と改善理由を確認し、比較する2版を選択します。
各評価項目の点差、変更されたページ・コマ、変更前後の描写・セリフ・ナレーション・概要を表示します。
差分はAIの説明から推測せず、JSONの値を直接比較します。ページ・コマの追加・削除も表示します。

各版の評価が複数ある場合は最新を比較します。未評価の版は空欄で、点数を推測しません。
過去版の採用は同じ内容を新しい最新履歴として保存します。同一JSONの採用元版に評価があればその旨を明記して表示し、再評価扱いにはしません。
「今回の改善理由」は保存時に記録した理由であり、実際の差分とは分けて表示します。

採用したい版を選んで「この版を脚本として採用」を押し、内容を確認して「現在の脚本を確定」を押します。
確定はユーザー判断で行えます。確定後に脚本の内容が変わると、既存画像や作画指示との不整合に注意する通知を表示します。
画像・作画指示は自動で書き換えません。各コマを見直し、必要なら再作画して再度確定してください。

## キャラクター・コマ画像を作る手順（第3段階）

人物・参照画像・作風は「キャラクター・作風」、コマ画像は「イラスト制作」で扱います。
作画指示とコマ画像の登録には、第2段階で保存したストーリーが必要です。キャラクターはストーリー取り込み前にも登録できます。

### 1. 作風とキャラクターを登録する

1. 「キャラクター・作風 → 基準画像・作風」の「プロジェクトの作風」に、白黒／カラー、線画、塗り、雰囲気などを入力して「作風を保存」を押します。作風はこのプロジェクトの各プロンプトに共通で反映します。
2. 「キャラクター・作風 → 手動設定」→「新規キャラクター」で名前・年齢・性別・髪型・髪色・目の色・体格・服装・性格・特徴を入力し、「キャラクターを保存」を押します。名前のみ必須です。年齢は「17歳」「不明」などの文字列で入力できます。
3. 別の人物を追加するときは再び「新規キャラクター」を選びます。既存の人物を選択して保存すると、その人物を更新します。同名の人物も別々に管理できます。
4. 削除する場合は「キャラクターを削除」を開き、対象名を確認してチェックを入れ、「このキャラクターを削除」を押します。

削除は一覧から非表示にする方式です。参照画像・候補画像・登録時の人物設定を残すため、ディスク上の画像は削除しません。
削除した人物を使っている作画指示は警告となるため、登場キャラクターを選び直して保存してください。

### 2. キャラクターの基準画像を作る

1. 「キャラクター・作風 → 基準画像・作風」で保存した人物を選び、「生成する向き・種類」を正面・斜め・全身・表情差分から選び、表情を指定します。
2. 日本語プロンプトを「プロンプトをコピー」またはダウンロードで取得し、ご自身でChatGPTへ貼り付けて画像を生成します。
3. ChatGPTで画像をダウンロードし、アプリの「キャラクターの参照画像」から選びます。種類とメモを入力して「参照画像を保存」を押します。
4. 正面・斜め・全身・表情差分などを繰り返し登録できます。最初の画像を基準画像とし、「基準にする参照画像」→「基準画像を選択」で変更できます。
5. 別の画像を生成するときは、参照画像をアプリからダウンロードし、ChatGPTへ**手動で添付**してください。プロンプト内のファイル名はアプリからダウンロードしたPNGの名前と一致します。

プロンプトをコピーしただけでは画像は送信されません。基準画像や補助画像も同じChatGPTの会話に添付してください。
同じ外見を保つための指示は含めますが、実際に生成された顔立ち・服装などはユーザーが目で確認します。

### 3. コマごとの作画指示とプロンプトを作る

1. 「イラスト制作 → コマ制作ワークスペース」でページ・コマを選び、「作画指示を編集」をオンにします。保存済みストーリーの描写・セリフ・ナレーションが表示されます。
2. 登場キャラクターを選び、場所・時間帯・表情・ポーズ・カメラ角度・構図を設定します。複数人の場合は「ルナ：笑顔、ソラ：驚き」のように表情を指定できます。
3. 「このコマの作画指示を保存」を押します。指示はストーリーJSONを変更せず、別に保存します。
4. 作風・キャラクター設定・作画指示・ストーリーを組み合わせた日本語プロンプトが表示されます。コピーして、人物の参照画像と一緒にChatGPTへ渡してください。

プロンプトは外見の統一を指示し、**セリフ・吹き出し・文字・ナレーションを画像に描き込まない**方針です。
セリフは場面の意味を伝える参考情報として渡します。登場キャラクターを選ばない場合は、人物を追加しない背景中心の指示になります。
未保存の設定はプロンプトに反映しません。新しい内容を使う場合は明示的に保存してください。コマ切り替えではセッション内の下書きを保持します。

### 4. コマ画像を登録・採用する

1. 「イラスト制作 → コマ制作ワークスペース」で対象のページ・コマを選び、ChatGPTからダウンロードした画像を選択します。
2. 「候補画像を保存」で登録します。同じコマに複数の候補を追加できます。同じファイル名でも上書きしません。
3. 候補を見比べ、「採用候補を選ぶ」→「選んだ候補を採用」を押します。新規登録だけでは採用になりません。
4. 「イラスト制作 → 画像履歴」で、ページごとの採用画像を確認します。未採用のコマも表示します。合成は「漫画ページ編集」、出力は「完成・書き出し → PNG・PDF書き出し」で行います。

採用を変更しても過去の候補は削除しません。候補ごとの「登録時の作画条件」で、その時の描写・作風・人物・作画指示を確認できます。
この記録は登録時点のアプリの設定で、ChatGPTで実際に使ったプロンプトを自動取得するものではありません。

ストーリーのコマ内容を変更すると、以前の作画指示・画像に警告が付きます。指示を確認して保存し直すと、現在の内容に結び直せます。
以前の画像を採用する場合は、警告を確認して選んでください。
コマ数・ページ数を減らしても画像は残り、「現在のストーリーにないコマの画像履歴」から確認できます。
作風やキャラクターの変更後も画像は自動再生成しません。必要に応じて新しい候補を追加します。

### 取り込める画像

- PNG・JPEG・WebPの静止画。1ファイル20MB・2400万画素以下です。アニメーションやHEICは取り込めません。
- 拡張子だけでなくPillowで画像の内容を検証し、向きの情報を反映したPNGとして保存します。
- 透過画像は透過を維持し、EXIFや画像内コメントなどのメタデータは保存時に除きます。元のダウンロード画像そのものは変更しません。
- 変換後に20MBを超える画像もエラーになります。その場合は元の画像を小さくして再登録してください。
- 参照画像と採用画像はダウンロードできます。アプリの画像候補を消す操作は用意していません。

## 保存先とデータ

プロジェクトの標準保存先はリポジトリ内の `data/projects/<UUID>.json` です。
JSONはUTF-8で日本語をそのまま保存し、タイトルをファイル名に使わないため、同名の企画も保存できます。
一時ファイルに書いてから置き換え、保存途中の失敗で既存のJSONが壊れることを防ぎます。
壊れたJSONは一覧に警告を表示し、正常なファイルは引き続き読み込みます。

ストーリーは `data/projects/<UUID>/story_history.json` に別保存します。
取り込み・ページ編集・復元のたびに、UUID・UTC日時・操作種別・ストーリー全体を記録します。最新の版が現在のストーリーです。
既存のプロジェクトJSONを移行する作業は不要です。プロジェクトを開くと対応する履歴を読み込みます。
同時保存はmacOS/Linux標準のファイルロックと版IDの確認で保護します。保存競合が表示された場合は、最新の内容を確認してからやり直してください。
履歴が壊れている場合は警告を表示し、上書きを停止します。手動で内容を削除せず、バックアップから復旧してください。

第3段階のデータも同じローカルの保存領域に配置します。

```text
data/projects/
├── <プロジェクトID>.json
└── <プロジェクトID>/
    ├── story_history.json     # 第2段階のストーリー履歴
    ├── editorial.json         # 参考作品・分析・評価・脚本確定の履歴
    ├── artwork.json           # キャラクター、作風、作画指示、候補・採用の記録
    ├── composition.json       # ページ設定・コマ割り・吹き出しと編集前の履歴
    ├── assistant.json         # 制作提案・確認・採用・作画評価の履歴
    ├── assistant_pending.json # 採用保存の変更前後・再開状態
    ├── studio.json            # UI設定・成功した描画／出力の記録
    └── images/
        ├── references/        # キャラクターの参照画像（UUID.png）
        └── panels/            # コマの候補画像（UUID.png）
```

画像はMacで実行していればMac上のこのフォルダに保存されます。クラウドで動かしたアプリはクラウド上に保存します。
候補画像はページ番号・コマ番号に紐づけ、登録時のストーリー版とコマ内容も記録します。採用の変更履歴もJSONに残します。
第1・第2段階のデータはそのまま利用でき、既存JSONの移行操作は不要です。
既存のキャラクター・作画設定・画像も変更しません。参考作品・分析・評価はプロジェクト別の `editorial.json` に保存し、
改善の対応情報だけを `story_history.json` の版メタデータに追加します。受け渡すストーリーJSONの形式は変更しません。
設定JSONだけをコピーすると画像は含まれないため、必ずプロジェクトのフォルダ全体をバックアップしてください。
保存はファイルロックと版番号の確認を使い、保存失敗時は既存のJSON・画像を維持します。

`data/projects/` 内の利用者データはGit管理対象外です。バックアップにはフォルダ全体を別の場所へコピーしてください。
履歴は増えていくため、必要に応じてバックアップとディスク空き容量を確認してください。
保存先を変更するときは、起動前に環境変数を設定します。相対パスは起動したフォルダが基準になるので、絶対パスを推奨します。

```bash
export MANGA_DATA_DIR="$HOME/Documents/manga-projects"
python -m streamlit run app.py --server.address 127.0.0.1
```

主なJSON項目は次のとおりです。

| 項目 | 内容 |
| --- | --- |
| `schema_version` | JSON形式のバージョン（現在は1） |
| `id` | プロジェクトを識別するUUID |
| `title`, `genre`, `synopsis`, `page_count` | 入力した企画 |
| `created_at`, `updated_at` | UTC・タイムゾーン付きの作成／更新日時 |
| `workflow` | 将来の工程・完了済み工程・成果物パスの保存領域 |
| `budget` | 第1段階との互換用項目。現在の手動連携では未使用 |

`workflow` は将来の工程管理用で、現在は保存・再読み込みだけを行います。
ストーリーは保存済みの最新履歴から編集を再開できます。自動生成処理の再開機能はありません。
未対応の `schema_version` は読み込み時に警告となります。将来形式を変える際は、データ移行処理を追加する想定です。

## 品質チェック・修正管理（第9段階）

6工程はそのままです。プロジェクトを開き、**「完成・書き出し → 品質チェック・修正管理」**を選びます。
ホームの「品質チェック・修正管理を開く」からも移動できます。保存済みのストーリー・画像・設定からページ数、全コマ数、採用数、検出数、手動レビュー必要数、未解決タスク、最終確認済みページを算出します。
検査していない場合や制作データが変わった場合は「未検査／要再検査」です。ページを表示しただけでは、目視確認済みになりません。

### まず自動チェックする

1. 「自動チェック・最終確認」で、検査対象を選びます。通常は保存済みサイズのページPNG・PDFです。縦読み用には**SNS横幅600／1080px**も選べます。
2. **「自動チェックを実行」**を押します。実際に検査したページ件数を表示し、結果を履歴に保存します。実行できなかった検査は未完了と表示します。
3. 検出一覧から問題を選び、「検出箇所を編集する」で移動するか、「この検出結果を修正タスクにする」で管理対象にします。

検査するのは、脚本保存、作画指示の欠落・古い脚本版・人物ID、採用画像の有無・ファイル欠損・復号・古い生成元、コマ配置、空の表示用本文、未分割発言、文字の収まり、未対応文字、実際の描画エラーです。
コマの重複・枠外配置、フォント・文字配置は既存の検証・描画処理を再利用します。壊れたJSONは書き換えず読込エラーにします。
**画像内の顔・髪・手指・文字を認識する処理はありません。** これらは目視または任意のChatGPT画像レビューで確認します。

解像度は固定の「最低1024px」のような基準では判定しません。保存した出力幅から求めたコマ内側のピクセル数と、実際に読み込めた元画像寸法を比較します。
`cover` はトリミング倍率を含めた拡大率、`contain` は画像全体の表示倍率を使い、1倍を超える拡大を警告します。SNS選択時は縦読み出力でコマを拡大する倍率も加味します。
出力幅・ズーム・画像が変わったら再検査してください。解像度の警告は画質の目安であり、絵の内容や印刷品質の保証ではありません。
全ページ出力の画素数上限・縦読みの1コマ高さも、書き出しと共通の事前検証を使います。

### ページを一覧で目視レビューする

1. **「ページサムネイルを作成・更新」**またはページ一覧内の更新ボタンで、順番に縮小画像を作ります。
2. 「ページ一覧・手動レビュー」で全体を見ます。8ページなら4列の一覧です。多い作品は12ページずつ表示します。
3. 「○ページを確認」またはページ選択で対象を選び、**「選択ページをプレビュー」**を押します。原寸出力と同じ描画を600pxに縮小します。
4. 実際に見た後、**「このプレビューを目視確認した」**を押します。先に最新の自動検査・描画を成功させてください。
5. 「各コマの脚本・セリフ・登場人物・採用画像」で内容を確認します。
6. 顔・服装、背景の連続性、感情、人体、視線誘導、吹き出しの隠れ、セリフの順序の7項目を「未確認／問題なし／要修正／対象外」で入力し、**「手動レビューを保存」**を押します。

目視済みの7項目を一括で「問題なし」に設定する操作も用意しています。**押しただけでは保存されず、利用者が見てから保存します。**
レビューの回答はページごとに保持します。画像・脚本・設定が変わると要再確認になりますが、以前の回答やメモは残り、再入力せず再確認・保存できます。
別ページの配置変更だけで変更のないページの目視確認を無効にしません。脚本の版、共通の人物設定・作風・フォント変更は複数ページに影響するため、再確認を促します。

### 問題を修正して再確認する

- 自動検出から、または目視画面の「目視で見つけた問題を修正タスクにする」から登録します。対象ページ・任意のコマ、重要度、修正対象を指定できます。
- 画面上部の「次に修正する問題」や「修正タスク」から**「このタスクの対象画面へ移動」**を押します。
- 画像・作画指示の指摘は該当コマのワークスペースへ、吹き出し・レイアウトの指摘は対象ページの編集へ移動します。
- 対象画面で明示的に保存し、**「品質チェックへ戻る」**を押します。未保存のページ下書きは検査・出力に含みません。
- 状態を「未対応 → 対応中 → 修正済み／再確認待ち」へ更新します。現在の保存内容を人間が見直し、「現在の保存済み画像・設定を人間が再確認した」をオンにして「確認完了」を保存します。
- 対応不要ならその状態で記録します。同じ未解決の指摘を二重にタスク化する操作は拒否します。

重要度（高／中／低）と修正状態は別に表示します。完了後に対象データが変われば再確認待ちになります。
発見時の脚本版、作画・ページ編集の版と内容識別子、採用画像ID、日時、対応履歴は削除しません。現在の脚本から外れたページ・コマも履歴として保持し、誤ったコマには移動しません。

### ChatGPTの画像レビューを使う（任意・手動）

1. 「ChatGPT画像レビュー（任意）」でページ、または比較する複数コマを選びます。必要なキャラクター基準・参照画像も自分で選択します。
2. 確認したい演出を書き、**「画像レビューの依頼を作成」**を押します。依頼ID・脚本版・対象と、折りたたみ外のプロンプト取得操作を表示します。
3. **「ChatGPTに渡すレビュー資料ZIPを生成」**→ダウンロードし、ZIPを展開します。選んだ完成ページPNG、Pillowで合成したコマ比較画像、選択した参照画像、説明・期待する演出・回答JSON形式入りプロンプト、添付明細が入ります。問題があれば警告も明細に残します。
4. **ユーザーがChatGPTへ画像を添付し、プロンプトを手動で送信**します。アプリが送信する機能はありません。
5. ChatGPTからのJSONをファイルに保存して「画像レビューJSONを検証・保存」で取り込みます。貼り付けも選べます。ファイルが初期値で、UTF-8 BOM・コードフェンスに対応します。
6. 指摘の根拠・改善案を確認し、必要なものだけ「このAI指摘を確認して修正タスクにする」で採用します。「対応不要」も記録できます。指摘0件の返答も人間による確認は別途必要です。

`request_id`、`story_version_id`、ページ・コマが依頼と一致するか検証します。本文欠損、重複した指摘・JSONキー、不正な重要度や型は拒否します。
古い画像・設定・脚本版に対する返答は取り込まず、新しい依頼作成を案内します。すでに取り込んだ過去の提案は残します。
AIの問題分類・内容・重要度・理由・改善案・修正対象・人間確認の要否を保存し、**未確認の提案**として扱います。画像や設定は自動変更しません。
ここでの評価は「完成画像・完成ページ」に対する主観的な補助で、既存の文章の作画評価とは別です。AIの評価は作品品質を保証しません。

### 最終確認と書き出し

「自動チェック・最終確認」に全ページの確認状況と次の未確認ページを表示します。
ページの自動検査・描画、プレビュー目視、手動7項目、未解決タスクの再確認を終えると、ページ画面の「このページを最終確認済みにする」で記録できます。
確認履歴では過去の検査・回答・対応を閲覧・JSONダウンロードできます。

**未確認の主観的な指摘や対応不要のタスクだけで、出力を禁止しません。** 警告を確認して「PNG・PDF・縦読み書き出しへ」で進めます。
書き出し画面から直接進む場合も未検査・未確認・未解決を警告し、利用者が「出力ファイルを生成」を押せます。
文字が収まらない・フォント未対応などの描画不能エラーは、従来どおり出力処理で停止します。画像の欠損は従来どおりプレースホルダーと警告になります。

### 保存先・安全性・テスト用データ

品質データは `<MANGA_DATA_DIR>/<プロジェクトID>/review.json`、縮小画像は同じ場所の `review_previews/` に保存します。
自動検査、手動回答、確認記録、タスク、画像レビュー依頼・提案・採否、更新履歴を分離して保存します。
更新時はmacOS/Linux共通のファイルロック、レビュー版番号と制作データの変更検知、一時ファイルからの原子的置換を使います。競合・保存失敗は理由と再読み込み／権限・容量確認を案内します。
`story_history.json`、`editorial.json`、`assistant.json`、`artwork.json`、`composition.json`、`studio.json`、元画像・参照画像を品質機能から書き換えません。以前の完成ファイル生成記録も維持します。
`MANGA_DATA_DIR` の外部保存先を使い、更新前はプロジェクトのフォルダ全体をバックアップしてください。品質JSONと縮小画像も同じバックアップに含まれます。自動削除・圧縮・履歴の消去はありません。

原寸画像はページ・コマ単位に読み込み、一覧は180pxの縮小PNGだけを表示します。検査・縮小一覧の生成・資料ZIP作成は明示操作時だけです。
画面は選択した作業だけを描画し、プレビューは容量制限付きキャッシュで再利用します。画像ファイル・設定・フォントが変わると指紋が変わり、古い結果を使いません。

Linux・Python 3.11.17・Streamlit 1.40.2で、600px出力の8ページ24コマを測定しました。
自動検査約1.17秒、8サムネイルの生成約115ms、生成済み8枚の取得約0.88msで、再表示時の元画像読み込みは0回でした。
単一実行の参考値で、Mac実機の速度や旧工程との比較ではありません。[計測・ブラウザ確認記録](benchmarks/review_stage9.json) に条件を記載しています。

APIなしで動かす8ページ24コマの架空作品と模擬AI返答の生成手順は [examples/quality_review/README.md](examples/quality_review/README.md) にあります。
空の専用フォルダにだけ生成し、ユーザーデータには触れません。テスト画像はローカルで描いた図形で、実際の漫画の品質評価を行った結果ではありません。

## 漫画ページを編集・出力する（第8段階）

### 最短の操作手順

1. 「イラスト制作」で必要な画像を採用し、「漫画ページ編集」でページを選びます。ページ数・コマ数は現在のストーリーJSONから取得します。
2. 初期選択の **「ビジュアル編集」** を使います。新規ページは「上段を大きく・下段は右→左」と、コマを埋める表示が初期値です。空のセリフ・ナレーション枠は作りません。
3. 右の「編集する対象」で「○コマ・画像配置」を選び、**画像の表示方式・横位置・縦位置・ズーム倍率**を調整します。左のプレビューで見切れを確認します。「画像全体を表示」では余白を許し、ズームを適用しません。
4. 吹き出しをプレビュー上でクリックし、**ドラッグで移動、四隅・辺の青いハンドルでサイズ変更**します。ドラッグ中は青枠を動かし、離すと本文を再描画します。右の選択欄でも枠を選べます。
5. 右側で本文・話者・縦横書き・形・しっぽ・表示を編集します。横位置・縦位置・幅・高さのスライダーはドラッグの代替操作です。「文字サイズ・背景の詳細」で文字サイズ、可読サイズの下限、背景色・不透明度・枠線を調整できます。
6. **「ページの編集を保存」**で初めて確定します。画像・文字枠の操作や提案適用だけでは保存しません。「キャンセル（保存済みに戻す）」、セッション内で最大30操作の「下書きを1つ戻す」も使えます。
7. 「保存後の完成プレビュー」を開き「ページをプレビュー・再描画」で保存結果を確認します。「完成サイズでプレビュー（高品質）」が初期値で、必要ならオフにして600pxの軽量表示にできます。「完成・書き出し → PNG・PDF書き出し」でサイズ・余白・日本語フォントを設定し、ファイルを生成・ダウンロードします。未保存の編集は出力に含めず、画面で通知します。

出力幅は600・1080・1600・2000px、縦横比は2:3・A判・正方形です。全体設定を変えると、同じ文字枠でも収まりが変わり得るため、完成プレビューを確認してください。
画面では完成サイズで合成した結果を最大600pxに縮小し、改行・トリミングを出力と揃えます。画像自体が持つ白い部分は自動除去せず、必要なら倍率・位置で調整します。顔の正確な自動検出は行いません。初期位置は右上・左上の縁を優先し、人物に重なる場合は手動で動かしてください。

### 話者別分割とナレーション

新規ページは、例えば `悠真：「あのさ……」` と `美咲：「ねえ……」` を**話者ごとの別枠**にします。同じ人物の複数発言も別のIDで管理します。話者名は内部の `speaker`、本文は `text`、分割前の原文は `source_text` に保存し、画像には話者ラベルを描きません。
明確な話者境界がない文章、閉じていない引用、分割上限を超える文章は原文を保持して「要確認」にします。推測で話者を付けたり、文を落としたりしません。右の編集欄で確認・分割してください。

**旧ページの吹き出しは自動分割・上書きしません。** 「脚本から話者別の分割・サイズ調整をやり直す」を開きます。
「脚本から吹き出しを提案」で話者・本文・サイズ案を一覧確認し、必要なら「分割案をページでプレビュー」をオンにします。
内容確認のチェック→「分割・サイズ調整案を下書きへ適用」→ページ保存の順に操作します。適用前後の比較・キャンセルができ、保存前の枠は保存履歴へ残ります。提案後に別の編集をした場合は、提案を作り直してください。

ナレーションはセリフとは別の `kind` を持つ四角い枠です。新規枠はしっぽなし、文字量に合わせた小さい初期サイズ、半透明の背景にします。例えば「卒業まで、あと7日。ずっと言えなかったことがある。」をコマ全体へ広げません。
枠が小さすぎる場合は「この枠を文字量に合わせる」を使うか、サイズを広げます。自動位置は顔検出の結果ではないため、重なり・読み順の確認は利用者が行います。

### 下書き・比較・復元と数値編集

「変更前後を比較」で編集開始時と現在の下書きを比較します。枠外の座標は警告し保存を止め、最後の有効なプレビューを残します。文字の溢れ・欠損画像・古い脚本との不整合も表示します。文字が収まらない状態では書き出しできません。
入力後は欄外をクリックしてから工程を切り替えてください。受信済みの下書きはプロジェクト・ページ・脚本版ごとにセッション内に保持します。再読み込み・アプリ終了では消えます。脚本更新後は古い版へ自動適用せず、古い下書きをJSONで取得できます。
他の保存と競合した場合は下書きを保持して保存を拒否します。下書きを取得し、キャンセルで最新版へ戻って必要な変更を入れ直してください。容量不足や保存失敗でも既存JSONは上書きしません。

「保存した編集履歴から復元」で対象を選び、配置・文章を確認し、復元チェックとボタンを押します。復元前の保存済みページも履歴に追加します。現在のコマ数と異なる履歴はそのまま復元せず、元の履歴を保持します。
ページを開いた直後に旧ページの見た目を変えたり、既存の画像・生成記録を消したりしません。

**従来の数値編集も残しています。** 「編集方法」を「従来の数値編集」へ切り替えると、元のコマ割りテンプレート、コマの手動座標、吹き出しの%座標・本文・表示設定、自由文の追加を使えます。レイアウトは縦積み／2列・右→左／上段大・下段右→左／右側大の4種類です。コマ番号が読み順です。数値編集には各保存ボタンがあり、ビジュアル編集の未保存下書きとは別に扱います。

### 日本語フォントと文字の収まり

Macでは標準のヒラギノ、Linuxではインストール済みのNoto CJKなどを自動検出します。
見つからない場合は、利用可能な日本語TTF・OTF・TTC・OTCのファイルパスを共通設定に入力してください。
Macの例は `/System/Library/Fonts/ヒラギノ角ゴシック W3.ttc` です。OSによって場所が違う場合はFont Bookで実ファイルを確認します。
環境変数 `MANGA_FONT_PATH` でも指定できます。フォントは自動ダウンロード・同梱しません。

新しい枠は句読点・閉じ括弧を行頭へ、開き括弧を行末へ置かない基本的な禁則処理を行います。横書きは句読点も改行候補にします。縦書きは上→下、列は右→左、縦用字形・長音の回転に対応します。
文字サイズはページ幅の約2.2〜2.5%から開始し、新規枠の下限は初期値2%です。下限でも収まらなければ警告・出力停止とし、文章を省略しません。旧枠は従来の配置・自動縮小条件を維持します。必要なら「可読サイズの下限を適用」で明示的に変更できます。
未対応文字も具体的なエラーにします。ルビ・縦中横・厳密な商用DTP組版には未対応です。RAQMなどの追加ネイティブライブラリは必要ありません。

### 検証用の1ページと性能計測

[examples/page_editor/story.json](examples/page_editor/story.json) は『君が忘れた、最後の約束』の指定3コマです。
テストでは、**先に保存・採用した図形のテスト画像**を読み込み、上段1コマ・下段右→左の2コマへ合成します。実際の作品画像・AI生成画像を使った検証ではありません。画像生成APIは使いません。
同じ保存済み画像で、トリミング・複数話者・ナレーション・ドラッグ・リサイズ・保存・再読み込み・PNG/PDF/SNS出力を確認しています。

```bash
python scripts/demo_page_editor.py --output /tmp/manga-page-demo
python scripts/benchmark_page_editor.py --output /tmp/manga-page-timing.json
```

デモは空の出力フォルダだけを使い、PNG・PDF・縦読みZIP・600pxプレビュー・検証JSONを作ります。利用者データには触れません。
Linux・Python 3.12の実測では、1080px合成→600px表示は初回171.10ms、コマキャッシュ利用時の中央値45.40ms、1コマの位置変更時74.38msでした。変更コマだけ1件再描画し、画像ファイルの再読み込みは0件でした。UIでは結果自体もキャッシュし、同じ下書きの再表示は合成処理を省きます。
条件・全サンプル・実ブラウザ検証結果は [benchmarks/page_editor_stage8.json](benchmarks/page_editor_stage8.json) に記録しています。Mac実機の速度・Safariでの実測は未確認です。

### 出力形式

| 形式 | 内容 |
| --- | --- |
| 表示中ページのPNG | 設定サイズの1ページ。DPI情報を含むフルカラーPNG |
| 全ページのPNG（ZIP） | `page_001.png` からページ番号順に格納 |
| 全ページのPDF | 全ページを1ファイルに格納。日本語も画像化したPDFなので、閲覧先でのフォント設定は不要（文字選択は不可） |
| 縦読みSNS画像（ZIP） | 横幅600／1080px、ページ順・コマ番号順に1列へ再配置。ページで合成したコマを同じ配置のまま拡大縮小。コマを途中で切らず、高さ8000px以内のPNGへ分割。対応表 `reading_order.json` を同梱 |

PDFは各ページの閲覧順が1、2、3…となります。見開きの綴じ方向や印刷用トンボは設定しません。
縦読みは全ページまたは表示中ページだけを選べます。コマの縦横比を保つため、極端に縦長のコマは調整を求めます。
メモリ使用量を抑えるため、一度の全ページ・縦読み出力は合計6000万画素までです。上限時は横幅を小さくするか、ページ単位で出力してください。
完成ファイルはブラウザからMacへダウンロードします。アプリの保存領域に完成ファイルを自動蓄積しません。

### 編集データと既存データの保護

ページ設定はプロジェクト別の `composition.json` に分離し、ストーリー・キャラクター・参考作品・候補画像のJSON形式は変えません。
トップの `schema_version: 1` を維持し、ページの任意項目 `editor_version: 2` と `image_placements`、文字枠の `speaker`・`kind`・`source_text`・背景色・不透明度・枠線・最小文字サイズ・文字配置形式を追加しました。
`image_placements` はコマ番号をキーに `mode`（cover/contain）、`x`・`y`（0〜1）、`zoom`（1〜4）を持ちます。情報がない旧ページはcontainで描画し、自動追記しません。吹き出しの `box` はコマの枠線内側を0〜1とした位置・幅・高さです。

設定の保存ごとに編集前の内容を `history` に残し、ファイルロックと版番号で保存競合を防ぎます。
JSONが壊れている場合は上書きを停止します。バックアップはアプリを終了して**保存先フォルダ全体**をコピーしてください。
`history` は変更前のページ・共通設定を保持します。ビジュアル編集から過去のページ編集を明示的に復元でき、復元前のページも履歴に追加します。

脚本変更後は、コマ数が同じなら配置を引き継ぎ、旧枠の脚本追従文だけ更新します。分割・専用本文は自動で変えません。コマ数が異なる場合は一時的な自動配置と安全な全体表示を使い、確認なしの新規トリミングは行いません。
画面・出力時に不整合の可能性を通知します。専用の文章や採用画像は自動変更しないため、確認して保存し直してください。
以前の配置は保存時の履歴に残り、減ったページやコマの画像も削除しません。

## AI制作アシスタント（第5段階）

ストーリー保存後、人物提案は「キャラクター・作風」、参考作品候補は「企画・ストーリー」、作画提案・評価・改善は「絵コンテ・作画指示」から使えます。AIへの送信と返答の受け取りは引き続き手動です。
**依頼作成やJSON取り込みだけでは、既存の確定設定は変わりません。**

### 共通の使い方

1. プロジェクトを開き、必要なら「制作テーマ・補足」を入力します。不明なら空欄で構いません。
2. 対応する制作メニューと作業から支援機能を選び、「○○の依頼を作成」を押します。ストーリー版、依頼ID、対象コマ、既存設定のスナップショットとプロンプトを保存します。
3. 上部の「プロンプトをコピー」またはダウンロードを使い、自分でChatGPTに貼り付けます。返答形式もプロンプトに含まれます。
4. 返答JSONを貼り付けるか、UTF-8のJSONファイルを取り込みます。Markdownのコードフェンス、UTF-8 BOMにも対応します。上限は1MBです。
5. 「提案一覧と既存内容の比較」で全件を確認します。「確認・編集する提案」を選ぶと実際の差分と確認事項を表示します。「選んだ提案だけ編集」で必要な箇所を直し、**提案の編集を保存**します。この時点でも既存設定は変わりません。
6. 「採用候補」のチェックを付けます。1件ずつ、または「確認待ちをまとめて選択」で全件を選べます。確認事項と差分を確認した承認チェックを付け、「選択した提案を採用」で初めて確定設定に反映します。
7. 不要な提案はチェックして「選択した提案を見送る」を押せます。見送ったものを確認待ちへ戻すこともできます。未選択の設定・画像は変更しません。

最新依頼の進行状態は「未作成・提案待ち・確認待ち・採用済み・見送り」などで表示します。
依頼ごとに複数の返答を保存でき、「表示する生成依頼」「表示する提案履歴」で以前の候補も閲覧できます。
採用済みの同じ提案を再採用して二重登録することはできません。新しい改善は新しい依頼・提案として保存します。
フォームの未保存内容は依頼・提案を切り替える前に保存してください。

### A：キャラクター一括生成

保存済みストーリーと既存人物の設定をChatGPTへ渡し、登場人物・外見・性格・身長・役割・視覚的な差別化を提案させます。
各非空項目の `provenance` に「ストーリー明記／AI提案／要確認」と根拠を持たせ、表で区別します。アプリで変更した項目は「ユーザー編集」として記録します。
AIが「明記」とした根拠も、アプリが作品内容を独立に検証したものではありません。採用前に確認してください。

既存人物の更新には `existing_id` を指定し、新規人物は `null` にします。確認画面の「反映先の人物」で変更できます。
既存人物を選ぶとそのID・参照画像・基準画像を維持して設定だけを更新します。新規IDはアプリが発行します。
同名候補は警告し、通常は登録を止めます。表記の全角・半角、大小文字、空白の差も重複候補として扱います。
別人を意図している場合だけ「同名候補がある場合も別の人物・作品として登録する」を選びます。
空の項目や確認事項は自動で推測補完しません。AIが新たに設計した設定は「AI提案」として扱います。

### B：参考作品候補

ジャンル・あらすじ・テーマ補足と既存参考作品から、漫画・小説・映画・アニメなどを提案させます。
参考理由、抽象的な技法、演出方法、自作への応用、確認状態と根拠を表示します。
AI返答は必ず「要確認」で取り込みます。「ユーザー確認済み」への変更は、利用者が内容を確かめてから確認・編集画面で行ってください。
確認状態はアプリによる事実確認を意味しません。未確認の作品情報は断定せず、固有の人物・台詞・展開の再現を避けます。
採用したものだけを既存の参考作品へ新規登録します。応用・確認状態・根拠は「メモ」に引き継ぎ、既存作品は上書きしません。
同じ作品名・媒体は通常重複登録を止めます。登録後は既存の参考作品管理・分析機能で編集・分析できます。
URLへアクセスしたり、外部サイトをスクレイピングしたりする処理はありません。

### C：作画指示一括生成

「出力対象」で**全コマ・指定ページ・指定コマ**を選べます。通常の8ページ24コマをまとめて依頼できます。
返答が長くなる場合はページ単位に分け、それぞれ依頼を作成してください。指定対象の一部が欠けたJSONはエラーになります。
ストーリー、登録人物、作風、既存指示を渡し、場所・時間帯・表情・ポーズ・カメラ・構図・背景・光・色彩・演出的役割・連続性を提案させます。
人物は登録済みのUUIDで指定します。新しい人物が必要ならAで採用してからCの依頼を作り直してください。

採用するコマだけにチェックを付けると、そのコマの指示だけを保存します。未採用コマ、候補画像、採用画像とその履歴は保持します。
採用画像があるコマの指示変更では、画像との不整合を警告します。画像一覧・ページプレビューでも、登録時の作画条件との変更を通知します。
画像は自動再生成しません。必要な画像をChatGPTで作り直し、従来の画像管理画面で候補登録・採用してください。

### D：作画評価・改善

対象コマに保存済みの有効な作画指示がある状態で評価依頼を作ります。未設定・脚本変更後の古い指示には確認を求めます。
評価は、整合性、構図、感情、表情・ポーズの自然さ、カメラ、連続性、人物の一貫性、読みやすさの8項目（0〜10点）です。
良い点・問題点・理由・改善案・対象ページとコマを保存し、100点換算の平均参考点も表示します。
**AIの採点は主観的な参考値で、作品の品質を保証しません。** ストーリー評価とは別に管理します。

評価JSONを取り込むと、評価を選んで全コマ・ページ・コマ単位の改善依頼を作れます。
返ってきた改善JSONもCと同じ確認・編集・選択採用を通します。元テーマ・世界観・人物設定・作風を維持するプロンプトです。
改善採用後は、新しい評価依頼を作って再評価します。「改善前後の作画評価・指示を比較」で各項目の得点差と、評価時点のJSONに基づく実際の指示差分を確認できます。
改善理由・原案・編集・採用時の変更前後は各提案の履歴に残ります。自動反復や自動送信は行いません。

### E：画像プロンプト一括出力

保存済みの有効な作画指示から、ページ・コマ番号付きの画像生成用プロンプトを一覧表示します。
共通作風（フルカラー等）、コマの文脈、人物外見、各作画項目、参照画像を手動添付する案内、文字・吹き出しを描かない指示を含みます。
各枠右上から1コマずつコピーでき、全件を `manga_image_prompts.txt` としてダウンロードできます。
未設定、脚本変更後の未確認の指示、削除済み人物のあるコマは出力せず、不足情報と必要な操作を表示します。
コピー・ChatGPTへの貼り付け・参照画像の添付・画像のダウンロードとアプリへの登録は、利用者が手動で行います。

### APIなしで試すサンプル

各機能で依頼を作り、「返答形式・サンプルJSONを表示」→「動作確認用の返答サンプルJSON」をダウンロードします。
現在の依頼ID・ストーリー版・人物IDに対応するため、ChatGPTを開かずにそのまま取り込み→提案編集→選択採用を試せます。
サンプルは架空のデモ設定・仮評価です。実作品へ採用する場合は必要な内容へ修正してください。
固定IDを使った形式例も [examples/assistant/](examples/assistant/) に5種類保存しています。固定例は任意の企画へそのまま取り込めません。

返答の共通項目は `schema_version`, `project_id`, `request_id`, `story_version_id`, `kind` です。生成プロンプトの値を変更しないでください。
提案は `items`、評価は `scores` と `summary` に分離します。必要なキーは返答ひな形を参照し、不明な設定は空文字、確認事項は `questions` の配列に記載します。
人物・提案IDの重複、対象外・欠番・欠けたコマ、存在しない人物ID、範囲外の評価点、不正なJSON・重複キーは保存前に検出します。

### 保存・互換性・途中失敗時の扱い

- `assistant.json`：依頼、プロンプト、対象ストーリー版と設定のスナップショット、提案原案・編集、採用状態、作画評価、改善・採用時の変更前後を保存します。
- `assistant_pending.json`：最後の採用保存の再開記録です。変更前後のJSONを持ち、完了後も `done` として残します。手動で削除しないでください。
- 採用先は既存の `artwork.json` または `editorial.json` です。`story_history.json`、`composition.json`、画像ファイルは変更しません。追加項目がない旧JSONもそのまま利用でき、移行操作は不要です。

取り込み・採用時に最新のストーリー版を確認します。依頼後に人物・作風や対象の作画指示を変更した場合も、その提案の取り込み・採用や評価利用を止め、新しい依頼を求めます。
一部採用後に残りの未変更コマを採用することはできますが、同じ古い依頼から別の返答を取り込む場合は依頼を作り直してください。
参照画像の追加だけでは人物の外見を上書きせず、最新の参照画像を保持して人物設定を採用できます。

保存はファイルロックと版番号で競合を検出し、一時ファイルからJSONを置き換えます。
2つのJSONにまたがる採用は、承認した変更を再開記録へ先に保存してから反映します。
途中で失敗すると片方だけが反映済みの場合があります。画面を更新し、「採用保存を再開」を押して完了してください。それまでは他画面の編集を避けます。
再開は二重登録を防ぎ、途中に別の編集があれば上書きを停止します。その場合は**保存フォルダ全体をバックアップ**し、再開記録と各JSONの差分を確認してください。
破損JSONも上書きせずエラーにします。履歴は増えるため、定期的にアプリを終了して保存先全体をバックアップしてください。

## テスト

仮想環境を有効にした状態で実行します。

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
```

テストは一時フォルダを使うため、実際の保存データを書き換えません。
